# 디버깅 도구

Pintos를 디버깅할 수 있는 많은 도구가 있습니다. 이 부록 은 그 들 중 일부 를 소개 합니다.

<a id="printf"></a>

## `printf()`

`printf()`의 가치를 과소평가하지 마십시오. Pintos에서 `printf()`가 구현되는 방식은 커널의 거의 모든 곳에서 호출 할 수 있습니다. 커널 스레드 또는 인터럽트 핸들러에 있든 간에, 거의 어떤 잠금을 지고 있는지 상관없이요. `printf()`은 단순히 데이터를 조사하는 것 이상의 용도로 유용하다. 그것은 또한 유용한 오류 메시지가 없이 커널이 충돌하거나 공황을 겪더라도 언제, 어디서 문제가 발생하는지 알아내는 데 도움이 될 수 있습니다. 전략은 `printf()`에 대한 호출을 서로 다른 문자열 (예를 들어 "\<1\>", "\<2\>", . . .) 로 오류가 있다고 의심하는 코드 조각에 퍼뜨리는 것입니다. \<1\>가 인쇄되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<2\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<2\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<2\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<2\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<2\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<2\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<1\>가 표시되어 있지 않은 경우 \<2\>가 표시되어 있지 않은 경우 \<2\>가 표시되어 있지 않은 경우 \<2\>가 표시되어 있는 경우 \<2\>가 표시되어 있습니다 학습된 내용을 바탕으로 새로운 작은 코드 영역에 더 많은 `printf()` 호출을 삽입할 수 있습니다. 결국 문제를 한 마디로 줄일 수 있습니다. 관련 기술에 대해서는 [세 가지 잘못](debugging_tools.md#triple-faults)을 참조하십시오.21121

<a id="assert"></a>

## ASSERT

인자은 유용합니다. 왜냐하면 그들은 문제가 발견되기 전에 문제를 일찍 파악할 수 있기 때문입니다. 이상적으로, 각 함수는 그 인자의 유효성을 확인하는 일련의 인자으로 시작되어야 합니다. (함수의 로컬 변수에 대한 초기화가 인자을 확인하기 전에 평가됩니다. 따라서 초기화에서 인자이 유효하다고 가정하지 않도록 주의하십시오.) 또한 당신이 무언가를 잘못 갈 가능성이 있다고 의심하는 장소에서 함수의 전체에 인자을 뿌릴 수 있습니다. 그들은 특히 루프 비변수를 검사하는 데 유용합니다.

Pintos는 인자을 확인하기 위해 `<debug.h>`에서 정의된 `ASSERT` 매크로를 제공합니다.

```
#define ASSERT(expression) { /* Omit details */ }
```

표현의 가치를 테스트합니다. 만약 0 (거짓) 로 평가한다면, 커널은 공황을 겪게 됩니다. 공황 메시지는 실패한 표현, 파일과 라인 번호, 그리고 배트트랙을 포함합니다. 자세한 내용은 [후퇴](debugging_tools.md#backtraces) 문서를 참조하십시오.

<a id="function-and-parameter-attributes"></a>

## 함수와 매개변수 속성

`<debug.h>`에서 정의된 이 매크로는 컴파일러에 함수 또는 함수 매개 변수의 특수 속성을 알려줍니다. 그들의 확장은 GCC에 특화된 것입니다.

------------------------------------------------------------------------

```
#define UNUSED { /* Omit details */ }
```

> 함수 매개 변수에 첨부하여 컴파일러에 해당 매개 변수가 함수 내에서 사용되지 않을 수 있음을 알려줍니다. 그것은 그렇지 않으면 나타나는 경고를 억제합니다.

------------------------------------------------------------------------

```
#define NO_RETURN { /* Omit details */ }
```

> 함수 프로토타입에 첨부하여 컴파일러에 함수가 돌아오지 않는다는 것을 알려줍니다. 컴파일러는 경고와 코드 생성을 정밀하게 조정할 수 있습니다.

------------------------------------------------------------------------

```
#define NO_INLINE { /* Omit details */ }
```

> 함수 프로토타입에 첨부하여 컴파일러에 함수를 직선으로 절대 방출하지 말라고 말합니다. 때때로 백트랙의 질을 향상시키는 데 유용합니다 ( 아래에 참조하십시오).

------------------------------------------------------------------------

```
#define PRINTF_FORMAT(format, first) { /* Omit details */ }
```

> 함수 프로토타입에 첨부하여 컴파일러에 함수가 `printf()`과 같은 형식 문자열을 논증 번호가 된 형식으로 (1) 취하고 그에 따른 값 논증은 먼저 번호가 된 논증에서 시작된다는 것을 알려줍니다. 이것은 컴파일러가 잘못된 논증 유형을 통과하면 알려줍니다.

<a id="backtraces"></a>

## 백트레이스

커널이 공황을 겪을 때, 그것은 "백트레이스"를 프린트합니다. 즉, 당신의 프로그램이 어디에 있는지에 대한 요약, 공황 당시 실행 중인 함수 내부의 주소 목록으로. 또한 `<debug.h>`에 프로토타입된 `debug_backtrace()`에 호출을 삽입하여 코드의 어느 시점에서든 백트레이스를 인쇄할 수 있습니다. `debug_backtrace_all()`, 또한 `<debug.h>`에서 선언된 것은 모든 스레드의 백트레이스를 인쇄합니다.

배트트랙에 있는 주소는 순위 여섯십자 숫자로 나열되어 있어 해석하기가 어렵다. 우리는 `backtrace`라는 도구를 제공하여 함수 이름과 소스 파일 라인 번호로 번역합니다. 첫 번째 논증으로 `kernel.o`의 이름을, 나머지 논증으로 백트레이스를 구성하는 여섯십자 숫자를 (`0x` 사전을 포함하여) 지정하십시오. 각각의 주소와 일치하는 함수의 이름과 소스 파일 라인 번호를 출력합니다.

배트트레이스의 번역된 형태가 왜곡되거나 의미가 없다면 (예를 들어 함수 A는 함수 B 위에 나열되어 있지만, B는 A를 호출하지 않습니다), 그것은 배트레이스가 스택에서 추출되기 때문에 커널 스레드의 스택을 손상시킨다는 좋은 신호입니다. 대체로, 당신이 백트랙으로 통과한 `kernel.o`은 백트랙을 생성한 커널과 같지 않을 수도 있습니다.

때때로 배트트랙은 부패 없이 혼란스러울 수 있습니다. 컴파일러 최적화는 놀라운 행동을 유발할 수 있습니다. 함수가 다른 함수를 최종 행동 (꼬리 호출) 으로 호출했을 때, 호출 함수는 전혀 후속으로 나타나지 않을 수 있습니다. 마찬가지로, 함수 A가 반환되지 않는 다른 함수 B를 호출할 때 컴파일러는 A 대신 관계없는 함수 C가 백트레이스에서 나타날 수 있도록 최적화 할 수 있습니다. 함수 C는 단순히 A의 직후에 메모리에 있는 함수입니다. 스레드 프로젝트에서, 이것은 일반적으로 테스트 실패에 대한 백트랙에서 볼 수 있습니다.

<a id="example"></a>

### 예제

예를 들어보죠. Pintos가 파일 시스템 프로젝트에 대한 실제 Pintos 제출에서 가져온 다음과 같은 호출 스택을 인쇄했다고 가정해보자:

```
Call stack: 0x800426eff 0x8004202fb 0x80042dc22 0x80042cf67 0x800422319
0x80042325a 0x40012c 0x400a96 0x400ac8.
```

다음은 아래와 같이 `backtrace` 유틸리티를 호출하여 백트레이스 정보를 명령 줄에 잘라 붙입니다. 이것은 `kernel.o`이 현재 디렉토리에 있다고 가정한다. 당신은 물론 다음의 모든 것을 하나의 셸 명령 줄에 입력 할 것입니다.

```
backtrace 0x800426eff 0x8004202fb 0x80042dc22 0x80042cf67 0x800422319
0x80042325a 0x400012c 0x400a96 0x4000ac8
```

배트트레이스 출력은 다음과 같습니다.

```
0x0000000800426eff: debug_panic (lib/debug.c:86)
0x00000008004202fb: file_seek (filesys/file.c:405)
0x000000080042dc22: seek (userprog/syscall.c:744)
0x000000080042cf67: syscall_handler (userprog/syscall.c:444)
0x0000000800422319: intr_handler (threads/interrupt.c:334)
0x000000080042325a: intr_entry (threads/intr-stubs.S:38)
0x000000000040012c: (unknown)
0x0000000000400a96: (unknown)
0x0000000000400ac8: (unknown)
```

(당신이 컴파일한 소스 코드와 당신이 사용한 컴파일러는 아마도 다르기 때문에, 자신의 커널 바이너리에서 위의 명령을 실행하면 정확히 같은 주소를 볼 수 없을 것입니다.) 백트레이스의 첫 번째 줄은 커널 패닉을 구현하는 함수인 `debug_panic()`를 참조합니다. 배트트레이스는 일반적으로 커널 공황으로 인해 발생하기 때문에, `debug_panic()`는 종종 배트트레이스에서 표시되는 첫 번째 함수이 될 것입니다. 두 번째 줄은 `file_seek()`을 공황에 빠진 함수로 나타냅니다. 이 경우 인자 실패로 인해 발생합니다. 이 예제에서 사용되는 소스 코드 나무에서, `filesys/file.c`의 405 라인은

    ASSERT (file_ofs >= 0);

(이 라인은 또한 인자 실패 메시지에서 인용되었다.) 따라서, `file_seek()`는 부정적인 파일 오프셋 인자을 통과했기 때문에 공황에 빠졌다. 세 번째 줄은 `seek()`가 `file_seek()`라고 불리는 것을 나타냅니다. 이 제출에서, `seek()`는 검색 시스템 호출을 실행합니다. 네 번째 줄은 시스템 호출 핸들러인 `syscall_handler()`이 `seek()`을 호출한 것을 보여줍니다. 다섯 번째와 여섯 번째 라인은 인터럽트 핸들링 진입 경로입니다. 나머지 줄은 `KERN_BASE` 아래의 주소입니다. 즉, 그들은 커널에서 아닌 사용자 프로그램에서 주소를 참조합니다.

<a id="gdb"></a>

## GDB

당신은 GDB 디버거의 감독 아래 Pintos를 실행할 수 있습니다. 먼저 `--gdb` 옵션을 사용하여 Pintos를 시작하십시오. `pintos --gdb -- run mytest`. 둘째, 같은 기계에 두 번째 터미널을 열고 gdb를 사용하여 'kernel.o'에 GDB를 호출하십시오.

    gdb kernel.o

다음 GDB 명령어를 발급합니다.

    target remote localhost:1234

이제 GDB는 로컬 네트워크 연결을 통해 시뮬레이터에 연결되어 있습니다. 이제 일반적인 GDB 명령어를 발급할 수 있습니다. 'c' 명령어를 발부하면 시뮬레이션된 BIOS가 통제를 취하고 Pintos를 로드하고 Pintos는 일반적인 방식으로 실행됩니다. Ctrl+C를 사용하여 프로세스를 언제든지 중단할 수 있습니다.

<a id="using-gdb"></a>

### GDB 사용법

터미널 명령 프롬프트에서 `info gdb`을 입력하면 GDB 매뉴얼을 읽을 수 있습니다. 여기 몇 가지 일반적으로 유용한 GDB 명령어가 있습니다:

- c \[GDB 명령\]

> hCtrl+Ci 또는 다음 브레이크포인트까지 실행이 계속됩니다.

- *함수* \[GDB 명령\]

- *파일: 라인* \[GDB 명령\]

- *주소* \[GDB 명령\]

> 함수, 파일 내 줄 또는 주소에서 브레이크 포인트를 설정합니다. (hex에서 주소를 지정하기 위해 '0x' 사전을 사용) Pintos가 실행되기 시작했을 때 GDB를 중지하기 위해 브레이크 메인을 사용하십시오.

- p *표현* \[GDB 명령\]

> 주어진 표현을 평가하고 그 값을 인쇄합니다. 만약 표현에 함수 호출이 포함되어 있다면, 그 함수는 실제로 실행됩니다.

- l *주소* \[GDB 명령\]

> 주소를 둘러싼 몇 줄의 코드를 나열합니다. (hex에서 주소를 지정하기 위해 '0x' 표본을 사용한다.)

- bt \[GDB 명령\]

> 위에 설명된 배트트레이스 프로그램에서 출력한 것과 유사한 배트트레이스 스택을 인쇄합니다.

- p/a *주소* \[GDB 명령\]

> 주소를 차지하는 함수 또는 변수의 이름을 인쇄합니다. (hex에서 주소를 지정하기 위해 '0x' 표본을 사용한다.)

- *함수* \[GDB 명령\]

> 해체 함수.

이 글을 읽는 분들에게 추가적인 팁: [pwndbg](https://github.com/pwndbg/pwndbg)와 같은 gdb 스크립트를 설치하세요. 이렇게 하면 더 쉬워요!

<a id="faq"></a>

### 자주 묻는 질문

- Emacs 내부에서 GDB를 사용할 수 있나요?

> 그래, 할 수 있어 Emacs는 GDB를 하위 프로세스로 실행하는 데 특별한 지원이 있습니다. M-x gdb를 입력하고 즉시 pintos-gdb 명령을 입력하십시오. Emacs 매뉴얼에는 "Debuggers"라는 섹션에서 디버깅 기능을 사용하는 방법에 대한 정보가 있습니다.

- GDB는 이상한 일을 하고 있습니다.

> GDB를 사용하는 동안 이상한 행동을 발견하면 세 가지 가능성이 있습니다. 수정된 Pintos의 버그, GDB와 Bochs의 인터페이스의 버그 또는 GDB 자체의 버그, 또는 원래의 Pintos 코드에서 버그. 첫 번째와 두 번째는 매우 가능성이 있고, 두 가지를 모두 진지하게 고려해야 합니다. 우리는 세번째가 덜 가능성이 있다고 믿습니다. 하지만 그것은 또한 가능합니다.

<a id="triple-faults"></a>

## 트리플 폴트

페이지 폴트 핸들러와 같은 CPU 예외 핸들러가 결실되거나 결실되어 있기 때문에 호출될 수 없을 때, CPU는 "다발 오류" 핸들러를 호출하려고 노력합니다. 이중 오류 핸들러 자체가 실종되거나 결함이 있는 경우, 그것은 "삼중 오류"라고 불립니다.

컴퓨터가 반복해서 재부팅되는 상황이라면 트리플 폴트일 가능성이 큽니다. 트리플 폴트에서는 `printf()` 디버깅도 사용할 수 없을 수 있습니다. `printf()`에 필요한 초기화가 끝나기도 전에 재부팅될 수 있기 때문입니다.

세 번째 오류를 디버깅하는 방법이 있습니다.

Pintos 코드에 있는 장소를 선택하고 무한 루프 `for (;;);`을 삽입하고 다시 컴파일하고 실행하세요. 두 가지 가능성이 있습니다.

- 기계가 다시 시작하지 않고 매달립니다. 만약 이런 일이 일어나면 무한한 루프가 실행되고 있다는 것을 알 수 있습니다. 즉, 리부팅을 일으킨 것은 *이후*이어야 합니다. 당신이 무한 루프를 삽입한 곳이죠. 이제 코드 순서에서 끝없는 루프를 나중에 움직입니다.

- 기계는 루프로 다시 시작됩니다. 만약 이런 일이 일어나면 기계가 무한 루프에 도달하지 못했다는 것을 알 수 있습니다. 따라서, 리부팅을 일으킨 것은 *이전*이어야 합니다. 당신이 무한 루프를 삽입한 장소입니다. 이제 코드 순서에서 끝없는 루프를 더 일찍 움직입니다.

  만약 당신이 "비너리 검색" 방식으로 무한 루프를 돌아다닐 경우, 이 기술을 사용하여 모든 것이 잘못되는 정확한 위치를 찾아낼 수 있습니다. 최소한 몇 분만 걸릴 겁니다.

## 도움말

`threads/palloc.c`의 페이지 할당자와 `threads/malloc.c`의 블록 할당자는 자유 시간에 메모리의 모든 바이트를 '0xcc'로 삭제합니다. 따라서, `0xcccccccc`와 같은 포인터를 삭제하려는 시도를 보시면, 또는 `0xcc`에 대한 다른 참조를 보시면, 이미 해방된 페이지를 재사용하려고 하는 가능성이 높습니다. 또한, 0xcc 바이트는 "Invoke interrupt 3"의 CPU 오프코드입니다. 그래서 `Interrupt 0x03 (#BP Breakpoint Exception)`과 같은 오류를 볼 경우, Pintos는 풀린 페이지 또는 블록에서 코드를 실행하려고 시도했습니다. 표현식 `sec_no < d->capacity`에 대한 인자 오류는 Pintos가 폐쇄되고 풀린 아이노드를 통해 파일을 접근하려고 시도했다는 것을 나타냅니다. 아이노드를 해방하면 시작 섹터 번호가 `0xcccccccc`로 정해집니다. 이는 1.6 TB 정도보다 작은 디스크에 유효한 섹터 번호가 아닙니다.
