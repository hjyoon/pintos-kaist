# 동기화

만약 스레드들 간의 자원 공유가 신중하고 통제된 방식으로 처리되지 않는다면, 그 결과는 보통 큰 혼란입니다. 이것은 특히 잘못된 공유가 전체 기계를 충돌시킬 수 있는 운영 체제 커널의 경우입니다. Pintos는 몇 가지 동기화 원시제를 제공하여 도움을 줍니다.

<a id="disabling-interrupts"></a>

## 인터럽트 비활성화

시크로네이션을 수행하는 가장 무리한 방법은 인터럽트를 비활성화하는 것입니다. 즉 CPU가 일시적으로 인터럽트에 응답하지 못하게 하는 것입니다. 인터럽트가 꺼지면 다른 스레드가 실행 스레드를 선행하지 않을 것입니다. 스레드 선행은 타이머 인터럽트가 주도하기 때문입니다. 만약 통상적으로 중간에 있는 경우, 두 개의 C 문장 사이에 있거나, 심지어 하나의 실행 속에서도 실행되는 스레드를 다른 사람이 언제든지 앞당길 수 있습니다.

그건 그렇고, 이것은 Pintos가 "예방할 수 있는 커널"이라는 것을 의미합니다. 즉, 커널 스레드들은 언제든지 예방할 수 있습니다. 전통적인 유닉스 시스템은 "예제할 수 없다", 즉, 커널 스레드는 스케줄러에 명시적으로 호출되는 경우에만 예제할 수 있다. (이용자 프로그램은 두 모델 모두에서 언제든지 선제할 수 있습니다.) 당신이 상상할 수 있듯이, 선제할 수 있는 커널은 더 명시적인 동기화가 필요합니다.

인터럽트 상태를 직접 설정할 필요가 없을 겁니다. 대부분의 경우 다음 섹션에서 설명된 다른 동기화 원시들을 사용해야 합니다. 인터럽트를 비활성화하는 주된 이유는 외부 인터럽트 핸들러와 커널 스레드를 동기화하는 것입니다. 이는 잠을 잘 수 없으며 따라서 대부분의 다른 형태의 동기화를 사용할 수 없습니다.

일부 외부 중단은 중단을 비활성화함으로써도 연기할 수 없습니다. **마스크가 불가능한 인터럽트** (NMI) 라고 불리는 이러한 인터럽트는 컴퓨터가 불타는 경우에만 사용되어야 합니다. Pintos는 마스크가 불가능한 인터럽트를 처리하지 않습니다.

중단을 비활성화하고 가능하게 하는 종류와 함수은 `include/threads/interrupt.h`에 있다.

------------------------------------------------------------------------

```
enum intr_level;
```

> INTR_OFF 또는 INTR_ON의 하나, 각각 인터럽트가 비활성화되거나 활성화되어 있음을 나타냅니다.

------------------------------------------------------------------------

```
enum intr_level intr_get_level (void)
```

> 현재 인터럽트 상태를 반환합니다.

------------------------------------------------------------------------

```
enum intr_level intr_set_level (enum intr_level level);
```

> 레벨에 따라 켜거나 끄는 것을 중단합니다. 이전 인터럽트 상태를 반환합니다.

------------------------------------------------------------------------

```
enum intr_level intr_enable (void);
```

> 중단을 켜고 이전 인터럽트 상태를 반환합니다.

------------------------------------------------------------------------

```
enum intr_level intr_disable (void);
```

> 중단을 끄고. 이전 인터럽트 상태를 반환합니다.

## 세마포어

세마포어는 두 개의 조작자와 함께 부정적 인 인터저입니다.

- "Down" 또는 "P" : 값이 양성될 때까지 기다립니다. 그리고 그것을 감소시킵니다.
- "UP" 또는 "V": 값을 증가시켜 (그리고 하나 있는 경우 대기 스레드를 깨우십시오).

0으로 초기화된 세마포어는 정확히 한 번 일어날 이벤트를 기다리는 데 사용될 수 있습니다. 예를 들어, 스레드 A가 다른 스레드 B를 시작하고 어떤 활동이 완료되었다고 B가 신호를 주고 싶어한다고 가정해보자. A는 0으로 초기화 된 세마포를 만들 수 있고, 시뮬레이션을 시작할 때 B로 전달하고, 그 다음 세마포를 "하하하" 할 수 있습니다. B가 활동을 끝낼 때, 세마포를 "올립니다". 이것은 A가 세마포를 "하하"하거나 B가 먼저 세마포를 "오프"하는지 여부와 상관없이 작동합니다.

예를 들어:

```
struct semaphore sema;

/* Thread A */
void threadA (void) {
    sema_down (&sema);
}

/* Thread B */
void threadB (void) {
    sema_up (&sema);
}

/* main function */
void main (void) {
    sema_init (&sema, 0);
    thread_create ("threadA", PRI_MIN, threadA, NULL);
    thread_create ("threadB", PRI_MIN, threadB, NULL);
}
```

이 예제에서, threadA는 `sema_down ()`에서 `sema_up ()`로 불리는 threadB까지 실행을 중지합니다.

1에 초기화된 세마포어는 일반적으로 리소스에 대한 접근를 제어하는 데 사용됩니다. 코드 블록이 리소스를 사용하기 시작하기 전에, 그것은 세마포를 "하하"하고, 리소스와 함께 완료되면 리소스를 "더 높이"합니다. 그러한 경우 아래와 같이 설명된 잠금이 더 적합할 수 있습니다.

세마포어는 또한 1보다 큰 값으로 초기화 될 수 있습니다. 이것은 거의 사용되지 않습니다. 세마포어는 Edsger Dijkstra에 의해 발명되었으며 처음으로 THE 운영 체제에서 사용되었습니다. Pintos의 세마포르 타입과 동작은 `include/threads/synch.h`에 명시되어 있습니다.

------------------------------------------------------------------------

```
struct semaphore;
```

> 신호등을 나타냅니다.

------------------------------------------------------------------------

```
void sema_init (struct semaphore *sema, unsigned value);
```

> 주어진 초기 값과 함께 새로운 세마포로 sema를 초기화합니다.

------------------------------------------------------------------------

```
void sema_down (struct semaphore *sema);
```

sema에서 "하하" 또는 "P" 동작을 수행하고, 그 값이 긍정적 인 값이 될 때까지 기다립니다. 그리고 1으로 감소합니다.

------------------------------------------------------------------------

```
bool sema_try_down (struct semaphore *sema);
```

> "Sema"에서 "down" 또는 "P" 동작을 기다리지 않고 실행하려고 합니다. sema가 성공적으로 디크레멘트 된 경우 true 또는 이미 0이면 false을 반환하여 기다리지 않고 디크레멘트 될 수 없습니다. 좁은 루프에서 이 함수를 호출하는 것은 CPU 시간을 낭비하기 때문에 `sema_down()`을 사용하거나 다른 접근법을 찾으십시오.

------------------------------------------------------------------------

```
void sema_up (struct semaphore *sema);
```

> sema에서 "up" 또는 "V" 동작을 수행하여 그 값을 증가시킵니다. 만약 세마를 기다리고 있는 스레드가 있다면, 그 중 하나가 깨어나게 됩니다. 대부분의 동기화 원시와 달리, `sema_up()`는 외부 인터럽트 핸들러 내부에서 호출될 수 있습니다.

세마포어는 내부적으로 인터럽트를 비활성화 ([장애를 차단 하는 것](synchronization.md#disabling-interrupts) 참조) 및 스레드 차단 및 해제 (`thread_block()` 및 `thread_unblock()`) 으로 구성되어 있습니다. 각 세마포어는 `lib/kernel/list.c`에서 연결된 목록 구현을 사용하여 대기 스레드 목록을 유지합니다.

## 락

잠자는 초기 값이 1인 세마포어와 같습니다 ([세마포르](synchronization.md#semaphores) 참조). 잠금의 "아래"와 동등한 값은 "해제"라고 하며, "하하"의 동작은 "수용"이라고 합니다.

세마포어와 비교했을 때, 잠기는 한 가지 추가적인 제한을 가지고 있습니다. 잠금을 획득하는 트헤드만이 잠금의 "주자"라고 불리는 것을 풀 수 있습니다. 만약 이 제한이 문제가 된다면, 그것은 잠금 대신 신호등을 사용해야 한다는 좋은 신호입니다.

Pintos의 로크는 "회복적"이 아닙니다. 즉, 현재 로크를 쥐고 있는 스레드가 로크를 획득하려고 시도하는 것은 실수입니다. 잠금 유형과 함수은 `include/threads/synch.h`에 명시되어 있습니다.

------------------------------------------------------------------------

```
struct lock;
```

> 락을 나타냅니다.

------------------------------------------------------------------------

```
void lock_init (struct lock *lock);
```

> lock을 새 락으로 초기화합니다. 처음에는 어떤 스레드도 소유하지 않습니다.

------------------------------------------------------------------------

```
void lock_acquire (struct lock *lock);
```

> 현재 스레드를 위해 lock을 획득합니다. 필요하면 현재 소유자가 해제할 때까지 먼저 기다립니다.

------------------------------------------------------------------------

```
bool lock_try_acquire (struct lock *lock);
```

> 기다리지 않고 현재 스레드를 위해 lock 획득을 시도합니다. 성공하면 true, 이미 소유자가 있으면 false를 반환합니다. 이 함수를 반복문으로 계속 호출하면 CPU 시간을 낭비하므로 `lock_acquire()`를 사용하세요.

------------------------------------------------------------------------

```
void lock_release (struct lock *lock);
```

> 현재 스레드가 소유해야 하는 잠금을 풀어줍니다.

------------------------------------------------------------------------

```
bool lock_held_by_current_thread (const struct lock *lock):
```

> 현재 실행 스레드가 lock을 소유하면 true, 아니면 false를 반환합니다. 임의의 다른 스레드가 락을 소유하는지 검사하는 함수는 없습니다. 호출자가 검사 결과를 사용하기 전에 소유 관계가 바뀔 수 있기 때문입니다.

## 모니터

모니터는 세마포어나 잠금보다 높은 수준의 동기화 형태입니다. 모니터에는 동기화되는 데이터, 그리고 모니터 잠금이라고 불리는 잠금, 그리고 하나 이상의 상태 변수들로 구성됩니다. 보호된 데이터에 접근하기 전에, 스레드는 먼저 모니터 잠금을 획득합니다. 그 다음에는 " 모니터에" 있다고 합니다. 모니터에 있는 동안, 스레드는 보호된 모든 데이터를 통제하고, 자유롭게 검토하거나 수정할 수 있습니다. 보호된 데이터에 대한 접근이 완료되면 모니터 잠금을 풀어줍니다.

조건 변수는 모니터의 코드가 조건이 진실이 될 때까지 기다리는 것을 허용합니다. 각 조건 변수는 추상 조건과 연관되어 있습니다. 예를 들어, "어떤 데이터가 처리하기 위해 도착했습니다" 또는 "이용자의 마지막 버튼 누르기 이후 10 초 이상이 흘렀다". 모니터의 코드는 조건이 진실이 될 때까지 기다려야 할 때, 연관된 상태 변수에 " 기다립니다". 이 상태는 잠금을 풀고 상태가 신호될 때까지 기다립니다. 다른 한편으로는, 이 조건 중 하나 가 사실 인 경우, 그것은 한 웨이터 를 깨우는 조건 을 "신기"하거나, 그들 모두를 깨우는 조건 을 "방송" 합니다.

모니터에 대한 이론적 틀은 C.A.R.Hoare가 제시했다. 그들의 실제 사용은 나중에 메사 운영 시스템에 대한 논문에서 상세히 설명되었습니다. 상태 변수 유형과 함수은 `include/threads/synch.h`에 명시되어 있습니다.

------------------------------------------------------------------------

```
struct condition;
```

> 상태 변수를 나타냅니다.

------------------------------------------------------------------------

```
void cond_init (struct condition *cond);
```

> 새로운 상태 변수로서 Cond을 초기화합니다.

------------------------------------------------------------------------

```
void cond_wait (struct condition *cond, struct lock *lock);
```

> lock(모니터 락)을 원자적으로 해제하고 다른 코드가 cond에 시그널을 보낼 때까지 기다립니다. 시그널을 받은 뒤에는 반환하기 전에 lock을 다시 획득합니다. 이 함수 호출 전에 lock을 보유해야 합니다. 시그널을 보내는 것과 대기에서 깨어나는 것을 합친 전체 과정은 원자적이지 않습니다. 따라서 일반적으로 `cond_wait()`의 호출자는 대기가 끝난 뒤 조건을 다시 검사하고 필요하면 다시 기다려야 합니다. 다음 절의 예제를 참고하세요.

------------------------------------------------------------------------

```
void cond_signal (struct condition *cond, struct lock *lock);
```

> 모니터 락 lock으로 보호된 cond에서 기다리는 스레드가 있으면 그중 하나를 깨웁니다. 기다리는 스레드가 없으면 아무 동작 없이 반환합니다. 이 함수를 호출하기 전에 lock을 보유해야 합니다.

------------------------------------------------------------------------

```
void cond_broadcast (struct condition *cond, struct lock *lock);
```

> 이 함수를 호출하기 전에 잠금을 유지해야 합니다.

<a id="monitor-example"></a>

### 모니터 예제

고전적인 모니터의 예는 하나 이상의 "생산자" 스레드가 문자를 작성하고 하나 이상의 "소비자" 스레드가 문자를 읽는 버퍼를 처리하는 것입니다. 이를 구현하기 위해서는 모니터 잠금 외에도 `not_full`와 `not_empty`라는 두 가지 조건 변수가 필요합니다.

```
    char buf[BUF_SIZE];     /* Buffer. */
    size_t n = 0;         /* 0 <= n <= BUF SIZE: # of characters in buffer. */
    size_t head = 0;        /* buf index of next char to write (mod BUF SIZE). */
    size_t tail = 0;         /* buf index of next char to read (mod BUF SIZE). */
    struct lock lock;         /* Monitor lock. */
    struct condition not_empty; /* Signaled when the buffer is not empty. */
    struct condition not_full;     /* Signaled when the buffer is not full. */

    ...initialize the locks and condition variables...

    void put (char ch) {
      lock_acquire (&lock);
      while (n == BUF_SIZE)    /* Can't add to buf as long as it's full. */
        cond_wait (&not_full, &lock);
      buf[head++ % BUF_SIZE] = ch;    /* Add ch to buf. */
      n++;
      cond_signal (&not_empty, &lock);    /* buf can't be empty anymore. */
      lock_release (&lock);
    }

    char get (void) {
      char ch;
      lock_acquire (&lock);
      while (n == 0)        /* Can't read buf as long as it's empty. */
        cond_wait (&not_empty, &lock);
      ch = buf[tail++ % BUF_SIZE];    /* Get ch from buf. */
      n--;
      cond_signal (&not_full, &lock);    /* buf can't be full anymore. */
      lock_release (&lock);
    }
```

상기 코드가 완전히 정확하기 위해서는 `BUF_SIZE`가 균등하게 `SIZE_MAX + 1`로 나뉘어야 한다는 점에 유의해야 한다. 그렇지 않으면 `head`이 처음 0으로 포장되면 실패합니다. 실제에서, `BUF_SIZE`은 보통 2의 힘이다.

## 최적화 장벽

최적화 장벽은 컴파일러가 장벽을 가로지르는 메모리 상태에 대해 가정하는 것을 막는 특수 문항입니다. 컴파일러는 바리어를 가로지르는 변수의 읽기 또는 쓰기를 재조정하거나 바리어를 가로지르는 변수의 값이 변경되지 않았다고 가정하지 않습니다. Pintos에서, `include/threads/synch.h`는 `barrier()` 매크로를 최적화 장벽으로 정의합니다.

최적화 장벽을 사용하는 이유 중 하나는 컴파일러의 지식 없이 데이터가 아시크론적으로 변경될 수 있는 경우, 예를 들어 다른 스레드 또는 인터럽트 핸들러에 의해. 예를 들면, `devices/timer.c`의 `too_many_loops()` 함수입니다. 이 함수는 타이머 틱이 발생하기 전까지 루프에서 바쁜 대기로 시작됩니다.

```
    /* Wait for a timer tick. */
    int64_t start = ticks;
    while (ticks == start)
        barrier();
```

루프에 최적화 장벽이 없다면 컴파일러는 루프가 결코 끝나지 않을 것이라는 결론을 내릴 수 있습니다. 왜냐하면 `start`와 `ticks`은 동일하게 시작되고 루프 자체는 결코 그들을 변경하지 않기 때문입니다. 그러면 함수를 무한한 루프로 "최적화"할 수 있고, 이는 확실히 바람직하지 않을 것입니다.

최적화 장벽은 다른 컴파일러 최적화를 피하기 위해 사용될 수 있습니다. 또한 `devices/timer.c`에 있는 `busy_wait()` 함수는 예입니다. 이 루프를 포함합니다.

```
    while (loops-- > 0)
      barrier ();
```

이 루프의 목표는 원래 값에서 0까지 루프를 계산함으로써 바쁜 대기입니다. 장벽이 없으면 컴파일러는 루프를 완전히 삭제할 수 있습니다. 왜냐하면 그것은 유용한 출력을 생성하지 않고 부작용이 없기 때문입니다. 장벽은 컴파일러가 루프 몸체가 중요한 효과를 가지고 있다고 척하도록 강요합니다.

마지막으로, 최적화 장벽은 메모리 읽기 또는 쓰기의 순서를 강요하는 데 사용될 수 있습니다. 예를 들어, 타이머 인터럽트가 발생할 때마다, 글로벌 변수인 `timer_put_char`의 문자가 콘솔에 인쇄되는 "자연"을 추가한다고 가정하지만, 글로벌 볼 변수인 `timer_do_put`이 사실이라면만. 인쇄하기 위해 `x`을 설정하는 가장 좋은 방법은 다음과 같은 최적화 장벽을 사용하는 것입니다.

```
    timer_put_char = 'x';
    barrier ();
    timer_do_put = true;
```

장벽이 없으면, 코드는 버그가 있습니다. 왜냐하면 컴파일러는 동일한 순서로 유지해야 할 이유를 볼 수 없을 때 작업을 다시 정리할 수 있기 때문입니다. 이 경우 컴파일러는 할당의 순서가 중요하다는 것을 알지 못하기 때문에 최적화가 그들의 순서를 교환할 수 있습니다. 실제로 이것을 할지는 알 수 없으며 컴파일러에 다른 최적화 플래그를 통과하거나 컴파일러의 다른 버전을 사용하는 것이 다른 행동을 유발할 가능성이 있습니다.

또 다른 해결책은 임무에 대한 방해를 비활성화하는 것입니다. 이것은 재편을 방지하지는 않지만 인터럽트 핸들러가 임무를 간섭하는 것을 방지합니다. 또한 장애를 비활성화하고 재활성화하는 추가 실행 시간 비용을 가지고 있습니다.

```
    enum intr_level old_level = intr_disable ();
    timer_put_char = 'x';
    timer_do_put = true;
    intr_set_level (old_level);
```

두 번째 해결책은 `timer_put_char` 및 `timer_do_put`의 선언을 `volatile`로 표시하는 것입니다. 이 키워드는 컴파일러에 변수가 외부에서 관찰될 수 있음을 알려주고 최적화를 위한 지위를 제한합니다. 그러나 `volatile`의 의미론은 잘 정의되어 있지 않기 때문에 좋은 일반적인 해결책은 아닙니다. 기본 Pintos 코드는 전혀 `volatile`을 사용하지 않습니다.

다음과 같은 것은 해결책이 아니기 때문에 잠기는 인터럽트를 막거나 컴파일러가 잠금을 보관하는 지역 내에서 코드를 재편하는 것을 막지는 않습니다.

```
    lock_acquire (&timer_lock);        /* INCORRECT CODE */
    timer_put_char = 'x';
    timer_do_put = true;
    lock_release (&timer_lock);
```

컴파일러는 외부로 정의된 함수의 호출을, 즉 다른 소스 파일에서 제한된 형태의 최적화 장벽으로 취급합니다. 특히 컴파일러는 외부로 정의된 함수가 어떤 정적 또는 역동적으로 할당된 데이터와 주소를 취득한 모든 로컬 변수를 접근할 수 있다고 가정합니다. 이것은 종종 명백한 장벽을 생략할 수 있다는 것을 의미합니다. Pintos가 몇 가지 명백한 장벽을 포함하고 있는 이유 중 하나입니다.

동일한 소스 파일에 정의된 함수 또는 소스 파일에 포함된 헤더에 최적화 장벽으로 의존할 수 없습니다. 이것은 정의 전에 함수를 호출하는 경우에도 적용됩니다. 왜냐하면 컴파일러는 최적화를 수행하기 전에 전체 소스 파일을 읽고 분석할 수 있기 때문입니다.
