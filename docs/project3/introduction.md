# 프로젝트 3: 가상 메모리

이제 당신은 Pintos의 내부 기능에 대해 조금 익숙해져야 합니다. 여러분의 OS는 적절한 동기화로 여러 개의 실행 스레드를 제대로 처리할 수 있고, 여러 사용자 프로그램을 동시에 로드할 수 있습니다. 그러나 실행할 수 있는 프로그램들의 수와 크기는 기계의 주요 메모리 크기 때문에 제한됩니다. 이 임무에서, 당신은 무한한 기억의 환상을 구축함으로써 그 한계를 제거 할 것입니다.

이 임무는 마지막 임무 위에 세워질 것입니다. 프로젝트 2의 시험 프로그램은 또한 프로젝트 3과 함께 작동해야 합니다. 프로젝트 3에서 작업을 시작하기 전에 프로젝트 2 제출의 모든 버그를 수정해야 합니다. 왜냐하면 그 버그가 프로젝트 3에서 동일한 문제를 일으킬 가능성이 높기 때문입니다.

프로젝트 3에서는 여러분의 편의를 위해 단계별로 안내합니다.

## 배경

<a id="source-files"></a>

### 소스 파일

이 프로젝트에 대해 `vm` 디렉토리에서 일하게 될 것입니다. `Makefile`은 `-DVM` 설정을 활성화하기 위해 업데이트됩니다. 우리는 엄청난 양의 템플릿 코드를 제공합니다. ***당신은 주어진 템플릿을 따라야 합니다. 즉, 주어진 템플릿에 기반하지 않은 코드를 제출하면 0pts를 얻습니다.*** 또한 템플릿에 "DO NOT CHANGE"라고 표시된 곳은 절대로 변경해서는 안 됩니다. 여기, 우리는 당신이 수정할 모든 템플릿 파일에 대한 몇 가지 세부 사항을 제공합니다.

- `include/vm/vm.h`, `vm/vm.c`

  가상 메모리의 일반적인 인터페이스를 제공합니다. 헤더에는 가상 메모리 시스템이 지원해야 하는 vm_type인 VM_UNINIT, VM_ANON, VM_FILE, VM_PAGE_CACHE의 정의와 설명이 있습니다. VM_PAGE_CACHE는 프로젝트 4용이므로 지금은 무시하세요. 또한 여기에 추가 페이지 테이블를 구현할 수 있습니다 (아래를 참조하십시오).

- `include/vm/uninit.h`, `vm/uninit.c`

  초기화되지 않은 페이지에 대한 동작을 제공합니다 (vm_type = `VM_UNINIT`). 현재의 디자인에 따르면 모든 페이지는 처음에는 초기화되지 않은 페이지로 설정되어, 그 다음 익명 페이지 또는 파일 백업 페이지로 변환됩니다.

- `include/vm/anon.h`, `vm/anon.c`

  익명 페이지의 동작을 제공합니다 (vm_type = `VM_ANON`).

- `include/vm/file.h`, `vm/file.c`

  파일 백업 페이지의 동작을 제공합니다 (vm_type = `VM_FILE`).

- `include/vm/inspect.h`, `vm/inspect.c`

  등급을 위한 메모리 검사 작업을 포함합니다. 이 파일을 변경하지 마세요.

이 프로젝트를 위해 작성하는 코드 대부분은 `vm` 디렉토리에 있는 파일과 이전 프로젝트에서 도입된 파일입니다. 여러분은 아마 몇 개의 파일을 처음 접할 것입니다. 예를 들어:

- `include/devices/block.h`, `devices/block.c`

  블록 장치에 섹터 기반의 읽기 및 쓰기 접근를 제공합니다. 이 인터페이스를 사용하여 블록 장치로 swap 파티션에 접근 할 수 있습니다.

<a id="memory-terminology"></a>

### 메모리 용어

먼저 기억과 저장 용어를 소개합니다. 이 용어들 중 일부는 프로젝트 2에서 익숙해야 합니다 ([가상 메모리 레이아웃](../project2/introduction.md) 참조) 하지만 대부분은 새로운 용어입니다.

<a id="pages"></a>

#### 페이지

때로는 가상 페이지라고도 불리는 페이지는 길이 4,096 바이트 (***페이지 크기***) 의 가상 메모리의 연속 영역입니다. 페이지는 ***페이지에 맞추어***이어야 합니다. 즉, 페이지 크기로 균등하게 나눌 수 있는 가상 주소에서 시작됩니다. 따라서 64-비트 가상 주소의 마지막 12 비트는 ***페이지 오프셋*** (또는 단순히 ***이산***) 이다. 상위 비트 는 곧 소개 될 페이지 테이블 에 있는 인덱스를 표시 하기 위해 사용 됩니다. 64비트 시스템에서는 4 레벨 페이지 테이블을 사용해서 가상 주소가 이렇게 생겼습니다.

    63          48 47            39 38            30 29            21 20         12 11         0
    +-------------+----------------+----------------+----------------+-------------+------------+
    | Sign Extend |    Page-Map    | Page-Directory | Page-directory |  Page-Table |    Page    |
    |             | Level-4 Offset |    Pointer     |     Offset     |   Offset    |   Offset   |
    +-------------+----------------+----------------+----------------+-------------+------------+
                  |                |                |                |             |            |
                  +------- 9 ------+------- 9 ------+------- 9 ------+----- 9 -----+---- 12 ----+
                                              Virtual Address

각 프로세스는 사용자 (虛擬) 페이지의 독립된 집합을 가지고 있으며, 이는 가상 주소 `KERN_BASE` (0x8004000000) 아래의 페이지입니다. 반면, ***커널 (버추얼) 페이지***의 집합은 전체적이며, 어떤 스레드나 프로세스가 실행되고 있음에도 불구하고 같은 위치에서 유지됩니다. 커널은 사용자 및 커널 페이지 모두에 접근 할 수 있지만 사용자 프로세스는 자신의 사용자 페이지에만 접근 할 수 있습니다. 자세한 내용은 [가상 메모리 레이아웃](../project2/introduction.md) 문서를 참조하십시오.

Pintos는 가상 주소와 작업하는 데 몇 가지 유용한 함수를 제공합니다. 자세한 내용은 [가상 주소](../appendix/virtual_address.md) 부문을 참조하십시오.

<a id="frames"></a>

#### 프레임

***프레임***, 때때로 ***물리적 프레임*** 또는 ***페이지 프레임***라고 불리는 것은 물리 메모리의 연속 영역입니다. 페이지와 마찬가지로 프레임도 페이지 크기와 페이지와 맞닿아 있어야 합니다. 따라서 64-비트 물리적 주소는 다음과 같이 ***프레임 번호*** 및 프레임 ***이산*** (또는 단순히 ***이산***) 로 나눌 수 있습니다.

                              12 11         0
        +-----------------------+-----------+
        |      Frame Number     |   Offset  |
        +-----------------------+-----------+
                  Physical Address

x86-64는 물리적 주소에서 직접 메모리에 접근하는 방법을 제공하지 않습니다. Pintos는 이를 통해 커널 가상 메모리를 직접 물리적 메모리에 매핑하여 작동합니다. 커널 가상 메모리의 첫 페이지가 물리적 메모리의 첫 프레임, 두 번째 페이지가 두 번째 프레임으로 매핑됩니다. 따라서 프레임은 커널 가상 메모리를 통해 접근 할 수 있습니다.

Pintos는 물리적 주소와 커널 가상 주소 사이의 번역 함수를 제공합니다. 자세한 내용은 [가상 주소](../appendix/virtual_address.md) 문서를 참조하십시오.

#### 페이지 테이블

***페이지 테이블***는 CPU가 가상 주소를 물리적 주소로, 즉 페이지에서 프레임으로 번역하기 위해 사용하는 데이터 구조입니다. 페이지 테이블 형식은 x86-64 아키텍처에 의해 결정됩니다. Pintos는 `threads/mmu.c`에서 페이지 테이블 관리 코드를 제공합니다.

아래 다이어그램은 페이지와 프레임 사이의 관계를 보여줍니다. 왼쪽의 가상 주소는 페이지 번호와 오프셋으로 구성됩니다. 페이지 테이블은 페이지 번호를 프레임 번호로 번역하여 오른쪽의 물리적 주소를 얻기 위해 수정되지 않은 오프셋과 결합합니다.

#### 스왑 슬롯

***스왑 슬롯***는 swap 파티션의 페이지 크기의 디스크 공간 영역입니다. 프레임에 비해 슬롯의 배치에 대한 하드웨어 제한이 더 유연하지만, 스위프 슬롯은 그렇게 하는 데 단점이 없기 때문에 페이지와 일치해야 합니다.

<a id="choices-of-implementation-performance-perspective"></a>

#### 자료 구조 선택 (성능 관점)

구현의 가능한 선택은 배열, 목록, 비트맵 및 해시 테이블을 포함한다. 배열은 종종 가장 간단한 접근 방식이지만 인구가 적은 배열은 메모리를 낭비합니다. 목록도 간단하지만 특정 위치를 찾기 위해 긴 목록을 통과하는 것은 시간을 낭비합니다. 배열과 목록 모두 크기를 변경할 수 있지만, 목록은 더 효율적으로 중간에 삽입 및 삭제를 지원합니다.

Pintos는 `lib/kernel/bitmap.c` 및 `include/lib/kernel/bitmap.h`에서 비트맵 데이터 구조를 포함한다. 비트맵은 각각의 비트의 배열이며, 각각은 진실 또는 거짓이 될 수 있습니다. 비트맵은 일반적으로 (동일한) 리소스의 집합에서 사용량을 추적하는 데 사용됩니다: 리소스 n가 사용되고 있다면 비트맵의 비트 ***n***가 사실입니다. Pintos 비트맵은 크기가 고정되어 있지만 크기를 변경할 수 있도록 구현을 확장할 수 있습니다.

Pintos는 또한 해시 테이블 데이터 구조를 포함한다 ([해시 테이블](../appendix/hash_table.md) 참조). Pintos 해시 테이블은 다양한 테이블 크기의 삽입 및 삭제 기능을 효율적으로 지원합니다.

더 복잡한 데이터 구조는 더 나은 성능이나 다른 이점을 가져올 수 있지만, 또한 불필요하게 구현을 복잡하게 만들 수 있습니다. 따라서 우리는 어떤 고급 데이터 구조 (예를 들어 균형 잡힌 바이너리 트리) 를 설계의 일부로 구현하는 것을 권장하지 않습니다.

<a id="managing-the-supplemental-page-table"></a>

### 보조 페이지 테이블 관리

***추가*** 페이지 테이블은 각 페이지에 대한 추가 데이터로 페이지 테이블을 보충합니다. 페이지 테이블의 형식에 의해 부과되는 한계 때문에 필요합니다. 이러한 데이터 구조는 종종 "페이지 테이블"이라고도 불립니다. 혼란을 줄이기 위해 "보완적"이라는 단어를 추가합니다.

추가 페이지 테이블는 적어도 두 가지 목적으로 사용됩니다. 가장 중요한 것은 페이지 폴트가 발생했을 때, 커널은 보조 페이지 테이블에서 오류가 발생한 가상 페이지를 검색하여 어떤 데이터가 있어야 하는지 알아냅니다. 둘째, 커널은 프로세스가 종료되면 어떤 리소스를 자유로울 것인지 결정하기 위해 보조 페이지 테이블을 참조합니다.

<a id="organization-of-supplemental-page-table"></a>

#### 보조 페이지 테이블의 구성

보조 페이지 테이블을 원하는 대로 정리할 수 있습니다. 조직에 대해 적어도 두 가지 기본 접근 방법이 있습니다: 세그먼트 또는 페이지 측면에서. 여기서 세그먼트는 연속적인 페이지 그룹, 즉 실행 가능한 또는 메모리 매핑 파일을 포함하는 메모리 영역을 의미합니다.

선택적으로, 페이지 테이블 자체를 사용하여 보조 페이지 테이블의 회원을 추적 할 수 있습니다. 이를 위해 `threads/mmu.c`에서 Pintos 페이지 테이블 구현을 수정해야 합니다. 우리는 이 접근 방식을 고급 학생들에게만 추천합니다.

<a id="handling-page-fault"></a>

#### 페이지 폴트 처리

보조 페이지 테이블의 가장 중요한 사용자는 페이지 폴트 핸들러입니다. 프로젝트 2의 페이지 폴트는 항상 커널이나 유저 프로그램의 버그를 의미했지만 프로젝트 3에서는 그렇지 않습니다. 파일이나 스왑 슬롯에서 페이지를 가져와야 한다는 뜻일 수도 있습니다. 이를 처리하려면 더 정교한 핸들러를 구현해야 합니다. `userprog/exception.c`의 `page_fault()`는 여러분이 구현하는 `vm/vm.c`의 `vm_try_handle_fault()`를 호출합니다. 이 핸들러는 대략 다음 작업을 수행해야 합니다.

1.  보조 페이지 테이블에서 오류가 발생한 페이지를 찾아보십시오. 메모리 참조가 유효하다면, 페이지에 들어가는 데이터를 찾기 위해 보조 페이지 테이블 항목을 사용하십시오. 이 데이터는 파일 시스템 또는 스왑 슬롯에 있을 수도 있고, 아니면 완전히 0 페이지일 수도 있습니다. 공유를 구현한다면 (즉, Copy-on-Write) 페이지의 데이터는 이미 페이지 프레임에 있을 수도 있지만 페이지 테이블에 있지 않을 수 있습니다. 보조 페이지 테이블에서 사용자가 접근하려는 주소에서 데이터를 기대해서는 안된다는 것을 표시하거나 페이지가 커널 가상 메모리에 있는 경우, 또는 접속이 읽기 전용 페이지에 글을 쓰려는 시도가 있는 경우, 접속이 무효입니다. 무효 접근은 프로세스를 종료하고 따라서 모든 자원을 자유롭게 합니다.

2.  페이지를 저장할 수 있는 프레임을 얻으십시오. 공유를 구현하면 필요한 데이터가 이미 프레임에 있을 수 있습니다. 이 경우 그 프레임을 찾을 수 있어야 합니다.

3.  데이터를 프레임으로 가져오세요. 파일 시스템에서 읽거나 교환, 제로링 등을 통해 공유를 구현하면 필요한 페이지가 이미 프레임에 있을 수 있습니다. 이 경우 이 단계에서 아무런 조치도 필요하지 않습니다.

4.  오류가 있는 가상 주소를 위한 페이지 테이블 항목을 물리적 페이지로 가리키십시오. `threads/mmu.c`에서 함수를 사용할 수 있습니다.

<a id="managing-the-frame-table"></a>

### 프레임 테이블 관리

프레임 테이블에는 각 프레임에 대한 항목이 있습니다. 프레임 테이블의 각 항목은 현재 해당 페이지를 점유하고 있는 페이지에 대한 포인터와 선택의 다른 데이터를 포함합니다. 프레임 테이블은 Pintos가 프레임이 없는 상태에서 퇴거을 위한 페이지를 선택함으로써 퇴거 정책을 효율적으로 구현할 수 있도록 합니다.

사용자 페이지에 사용되는 프레임은 `palloc_get_page(PAL_USER)`을 호출하여 " 사용자 풀"에서 얻어야 합니다. 일부 테스트 케이스가 예기치 않게 실패할 수 있는 "크 kernel pool"에서 분배를 피하기 위해 `PAL_USER`을 사용해야 합니다. 프레임 테이블 구현의 일환으로 `palloc.c`을 수정하면 두 풀 사이의 구별을 유지하는 것을 확인하십시오.

프레임 테이블에서 가장 중요한 작업은 사용하지 않은 프레임을 얻는 것입니다. 프레임이 자유로울 때 쉽죠. 자유롭지 않은 경우, 프레임은 프레임에서 어떤 페이지를 추방함으로써 자유로워야 합니다.

만약 어떤 프레임도 스바프 슬롯을 할당하지 않고 추방할 수 없다면, 하지만 스바프가 가득하다면, 실제 운영체제는 이러한 상황으로부터 회복하거나 예방하기 위해 다양한 정책을 적용하지만, 이러한 정책은 이 프로젝트의 범위를 벗어난다.

추방 절차는 대략 다음과 같은 단계로 이루어집니다.

1.  페이지 교체 알고리즘을 사용하여 추방할 프레임을 선택하세요. 아래 설명된 페이지 테이블의 "접근" 및 "더러운" 비트들은 유용하게 사용할 수 있습니다.

2.  프레임에 대한 참조를 참조하는 페이지 테이블에서 제거하십시오. 공유를 구현하지 않은 경우 한 페이지만 프레임을 참조해야 합니다.

3.  필요하다면 페이지를 파일 시스템에 적거나 교환할 수 있습니다. 추방된 프레임은 다른 페이지를 저장하는 데 사용될 수 있습니다.

<a id="accessed-and-dirty-bits"></a>

#### 접근 비트와 더티 비트

x86-64 하드웨어는 각 페이지에 대한 페이지 테이블 엔트리 (PTE) 에서 몇 개의 비트를 통해 페이지 교체 알고리즘을 구현하는 데 약간의 도움을 제공합니다. 페이지에 대한 모든 읽기 또는 작성에서 CPU는 페이지의 PTE에서 접근 된 비트 1을 설정하고 모든 작성에서 CPU는 ***더러운***을 1으로 설정합니다. CPU는 이 비트들을 0으로 다시 설정하지 않지만 OS는 그렇게 할 수 있습니다.

`aliases`, 즉 같은 프레임에 관한 두 (또는 더 많은) 페이지에 대해 알아야 합니다. 익명 프레임에 접근할 때, 접근 및 더티 비트들은 하나의 페이지 테이블 항목 ( 접근 위해 사용되는 페이지에 대한 항목) 에서 업데이트됩니다. 다른 애니메이션에 대한 접근 및 더티 비트는 업데이트되지 않습니다.

Pintos에서, 모든 사용자 가상 페이지는 커널 가상 페이지에 별명으로 표시됩니다. 이 별명을 어떻게든 관리해야 합니다. 예를 들어, 당신의 코드는 두 주소 모두에 대한 접근 및 더티 비트를 확인하고 업데이트 할 수 있습니다. 대안적으로, 커널은 사용자 가상 주소를 통해 사용자 데이터에 접근함으로써 문제를 피할 수 있습니다.

다른 별명은 공유를 구현하거나 코드에서 버그가 있는 경우에만 발생할 수 있습니다.

[페이지 테이블 접근 및 더티 비트](../appendix/page_table.md) 섹션에서 접근 및 더티 비트와 작업하는 함수에 대한 자세한 내용을 참조하십시오.

<a id="managing-the-swap-table"></a>

### 스왑 테이블 관리

스왑 테이블은 사용 중과 무료 스왑 슬롯을 추적합니다. 사용되지 않은 swap 슬롯을 선택하여 페이지를 프레임에서 swap 파티션으로 제거할 수 있도록 해야 합니다. 페이지가 다시 읽히거나 페이지가 교환된 프로세스가 종료되면 스왑 슬롯을 자유롭게 할 수 있어야 합니다.

`vm/build` 디렉토리에서 `pintos-mkdisk swap.dsk --swap-size=n` 명령어를 사용하여 n-MB swap 파티션을 포함하는 `swap.dsk`이라는 디스크를 생성하십시오. 그 후, `swap.dsk`은 자동으로 핑토를 실행할 때 추가 디스크로 부착됩니다. 또 다른 방법으로, `--swap-size=n`로 한 번의 실행에 임시 n-MB swap 디스크를 사용하도록 pintos에 말할 수 있습니다.

스왑 슬롯은 느슨하게 할당되어야 하며, 즉, 실제로 추방에 의해 요구되는 경우에만 할당되어야 합니다. 실행 가능한 데이터 페이지를 읽고 프로세스 시작 시 즉시 교환하도록 작성하는 것은 게으르지 않습니다. 특정 페이지를 저장하기 위해 스왑 슬롯을 미리 예약해서는 안 됩니다.

그 내용을 프레임으로 다시 읽을 때 스왑 슬롯을 풀 수 있습니다.

<a id="managing-memory-mapped-files"></a>

### 메모리 매핑 파일 관리

파일 시스템은 `read` 및 `write` 시스템 호출으로 가장 일반적으로 접근됩니다. 2차 인터페이스는 `mmap` 시스템 호출을 사용하여 파일을 가상 페이지로 "맵"하는 것입니다. 그 다음 프로그램은 파일 데이터에 직접 메모리 명령어를 사용할 수 있습니다. 파일 `foo`의 길이는 `0x1000` 바이트 (4kB, 또는 한 페이지) 가 있다고 가정합니다. `foo`이 `0x5000` 주소를 시작으로 메모리에 매핑되면 `0x5000. . .0x5fff` 위치에 대한 모든 메모리 접근는 `foo`의 해당 바이트에 접근합니다.

다음은 `mmap`을 사용하여 콘솔에 파일을 인쇄하는 프로그램입니다. 명령줄에 지정된 파일을 열고, 가상 주소 `0x10000000`에 매핑를 그리고, 지도된 데이터를 콘솔 (fd 1) 에 기록하고, 파일을 해제합니다.

```
#include <stdio.h>
#include <syscall.h>
int main (int argc UNUSED, char *argv[])
{
  void *data = (void *) 0x10000000;                 /* Address at which to map. */
  int fd = open (argv[1]);                          /* Open file. */
  void *map = mmap (data, filesize (fd), 0, fd, 0); /* Map file. */
  write (1, data, filesize (fd));                   /* Write file to console. */
  munmap (map);                                     /* Unmap file (optional). */
  return 0;
}
```

귀하의 제출은 메모리 매핑 파일에서 사용되는 메모리를 추적할 수 있어야 합니다. 이것은 지도된 지역에서 페이지 폴트를 적절히 처리하고 지도된 파일들이 프로세스의 다른 세그먼트를 겹치지 않도록 하기 위해 필요합니다.
